# Device buffers from a Bend program

The #14 ceiling was 5.31 ms with contiguous device buffers. This is the first
version that a **Bend program actually calls**: a C effect copies a Bend
`Array<F32>` to device memory, runs the tiled kernel, and writes the result back
into a new `Array<F32>`.

## How it works

- `bench/gpu/device_mm.bend` declares `Device.mm(a, b, c, m, n, k)` with a C
  twin.
- `bench/gpu/device_mm.c` (generated by `tools/embed_ptx.py`) dlopen's
  `libcuda.so.1`, loads the embedded PTX, and uses the driver API directly.
- A Bend `Array<F32>` block is **contiguous 32-bit elements, two per 64-bit
  cell** (`TAG_ARR`). The effect reads `((u32*)(e.mem + blk_loc(...)))[i]`,
  copies both operands to `cuMemAlloc` device buffers, launches the 16x16 tiled
  kernel, copies back, and writes the output cells into `blk_copy(e, c)`.
- JS twin: native-only (`device_mm.js` throws).

## Result, 1024x1024, checksum 268622200

| mode | ms | note |
|---|---:|---|
| cold | 195 | first call: CUDA context + module load |
| **warm** | **16** | cached context; includes host↔device copies and array conversion |
| Bend tree (2x2) | 95 | managed heap, no copies |
| standalone CUDA | 5.31 | no Bend array conversion; direct host buffers |

The warm effect is **5.9x faster than the tree** and produces the exact
checksum. The remaining 11 ms over the standalone is the host↔device copies,
the 1M-element host conversion, and `blk_copy`; a runtime-level path could
remove most of it.

## Limits

- Tied to Bend 2.0.40 internals (`blk_loc`, `blk_cls`, `blk_copy`,
  `f32_unbox`/`f32_rewrap`, `io_eff`). This is an effect prototype, not a stable
  API.
- `n` must be a multiple of 16; one device context is cached per process; no
  buffer reuse yet.
- Native only; the JS lane throws.
- The CUDA driver is loaded at runtime, so the build needs no `-lcuda`.
